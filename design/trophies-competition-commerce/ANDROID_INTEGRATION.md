# Android integration boundary

The current workspace has no Android Gradle project. `index.html` is browser-only. `shop-bridge.js` is a web adapter for a future native Android host; it refuses purchases in a browser and has no mock credit button. Product IDs are placeholders, and no real products exist yet.

The Android host must use Google Play Billing Library to query current product details, start a purchase, process pending and completed callbacks, and query purchases again on resume. Send a purchase token to a secure verification service with the signed-in game account. The service checks product/package/state with the Google Play Developer API, uses a unique token ledger, credits gems once or grants the permanent outfit, then consumes or acknowledges. Only a verified server response may call `CourierShop.receiveNativeState`. Do not call it from untrusted web content. Until the service URL, Play Console products, account binding and Android package are configured, the native host must report `available:false` and show no Buy button.

For an Android WebView, allow JavaScript only on packaged trusted assets; do not expose `shopRequest` to arbitrary sites. A local origin with controlled navigation is needed. The existing `window.CourierAndroid` haptics method can coexist with `shopRequest`. The game currently records completed runs through `recordRun` when supplied by a host; the host must reject ineligible results and never treat that JavaScript payload as proof for a prize-bearing public leaderboard.

Google's test environment: set up an internal test track and license tester accounts in Play Console. License testers get test payment instruments including approve, decline, delayed approve and delayed decline; test products can be restored/refunded/revoked. Internal track alone does not make in-app purchases free. Use a unique test package/product configuration and inspect orders and entitlement logs. See [Billing testing](https://developer.android.com/google/play/billing/test) and [internal testing](https://support.google.com/googleplay/android-developer/answer/9845334).

The local `results-server.cjs` is a development prototype for one best clean all-house light-spend result per player and level. Run `node results-server.cjs`; it binds only to `127.0.0.1:8787`. It has anonymous local player creation and no authentication or run replay; do not expose it on the internet or use it as the production leaderboard. Its `results-dev.json` is local test data. Production requires verified Play Games/account identity, a database, privacy controls, rate limits, and deterministic run validation. Google Play Games leaderboards may cover broad campaign rankings; a 200-to-2,000-level global minimum table and player-by-level records are better kept in this small operator service so the rules can grow later.
